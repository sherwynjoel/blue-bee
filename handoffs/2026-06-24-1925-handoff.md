Update is an **atomic Lua CAS** that advances only on a strictly-newer `recorded_at` — a late/older ping never regresses last-known, even under concurrent bursts.
- **Timescale history** (real): every accepted ping appended to the `GpsPing` hypertable via one parameterized multi-row `INSERT` (PostGIS `ST_MakePoint`), atomic, idempotent. The replay/audit record (§6.2).
- **`GET /v1/fleet/live`** (OWNER/DISPATCH/CSR) — all caller-org vehicles' last-known: Redis hot store, **fallback to the latest hypertable row** when Redis is cold. Org-scoped: a different org sees none of this org's vehicles.
- **`GET /v1/orders/:id/tracking`** (owning customer + staff) — last-known of EXACTLY the one vehicle on the order's active stop, scoped to the owning customer (cross-account/org → `404`). Single-vehicle response shape (privacy by construction). (Signed channel token + live WS = Increment 6.)

### Write-order design (last-known freshness under throttled history)
Redis CAS runs FIRST (keeps the hot store fresh even if history is momentarily slow — §10.4), then the Timescale append. On a history failure the caller retries: the CAS is a no-op (not strictly newer) and the hypertable insert is idempotent (ON CONFLICT) — so a retry reconciles both stores. `fleet/live` covers the inverse (Redis cold) via the Timescale fallback. No reliance on the scoped-extension inside raw SQL — every ping row and every fallback read carries an **explicit `org_id`** (the Increment-4 in-transaction-scoping lesson; the ingestion path uses no Prisma `$transaction`, so the hazard does not arise).
