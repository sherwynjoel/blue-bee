## What shipped

### The seam + provider (the only Stripe-SDK touch-points)
- **`PaymentProvider`** (`apps/api/src/payments/provider/payment-provider.ts`) — `PAYMENT_PROVIDER`
  token, mirrors `StorageProvider`/`EtaEstimator`. All amounts cross as integer **minor units**; every
  create carries a Stripe **idempotency key**.
- **`StripePaymentProvider`** (real `stripe` v17 SDK) — the SHIPPED prod path, env-selected when
  `STRIPE_SECRET_KEY` is present. createPaymentIntent / capture / refund / createInvoice /
  finalizeInvoice. Its **live test-mode network round-trip is the deferred run (parked (d))**;
  request-shaping is unit-tested with the SDK mocked.
- **`LocalPaymentProvider`** — deterministic, no-network; the default no-key path so the whole rail
  runs headlessly. **The deferred-OUTBOUND seam, NOT a stub of the inbound rail.**
- **`StripeEventVerifier`** — ALWAYS-REAL inbound signature verification (`stripe.webhooks.constructEvent`,
  local HMAC, no network), independent of which outbound provider is selected. `signTestPayload` wraps
  Stripe's real `generateTestHeaderString` for the e2e + proof.

### Take-payment core
- `POST /v1/orders/:id/payment-intent` (customer, own order) — amount **computed server-side from the
  approved Quote.total incl. Ontario HST** (`createPaymentIntentSchema` has NO amount field — the
  client can't influence the charge); returns ONLY the `client_secret`. Re-attempt reuses the pending
  intent's idempotency key (same intent → no second charge). Bounded by `PAYMENTS_MAX_ATTEMPTS` (4).
- **Charge-on-approval** is the tight default (PRD A5.1); capture-later is seam-ready via
  `PAYMENTS_CAPTURE_TIMING=on_delivery` (capture_method=manual + a capture() method) — the
  on-delivery TRIGGER is deferred (it belongs to the delivery/owner increment).

### The webhook — the source of truth
- `POST /v1/webhooks/stripe` (`@Public`, raw body via `NestFactory({ rawBody:true })` in `main.ts` AND
  the e2e `app.factory`; a SLASH route per the Inc-9 path-to-regexp lesson).
- Verify the **raw-body** signature → **400** on forged/unsigned/tampered. Then in ONE transaction:
  claim the event id in **`ProcessedStripeEvent`** (`INSERT … ON CONFLICT DO NOTHING` — the Inc-5
  pattern) **+ drive the state machine** → a row's existence means the event was fully applied
  (redelivery + concurrency are no-ops). Post-commit it fires receipt/dunning/dispute notifications.
- **Never trusts the client's "it succeeded"** — payment state advances ONLY from a verified event.

### State machines (webhook-driven, atomic, audited)
- **Payment** PENDING→SUCCEEDED|FAILED→REFUNDED (illegal → guarded no-op; re-apply is idempotent).
- **Invoice** DRAFT/ISSUED→PAID (invoice.paid / PaymentIntent success) | OVERDUE (invoice.payment_failed).
- **Refund** full + partial — refund ≤ captured via an **atomic optimistic reserve**;
  `charge.refunded` reconciles to Stripe's **authoritative refunded total** (idempotent) + records a
  SUCCEEDED row for any dashboard-initiated delta.
- **Dispute** OPEN→UNDER_REVIEW→WON|LOST|CLOSED — recorded + surfaced + alerted, **never adjudicated**.
- Order **billing state** mirrored onto `order.totals.paymentStatus` atomically in the webhook tx; the
  §5.1 fulfilment spine is NOT corrupted (only a conservative DELIVERED→INVOICED advance).
- Every transition writes an append-only `AuditLog` entry.

### Invoicing + receipts
- `POST /v1/orders/:id/invoice` (owner/finance) → Invoice + **InvoiceLine** rows from the quote (lines
  + the HST line), finalize/send, exercises the Stripe-Invoice outbound seam (stores `stripe_invoice_id`).
- A PaymentIntent success auto-generates the order's **PAID invoice = the customer receipt**.
- `GET /v1/orders/:id/payment` + `GET /v1/orders/:id/invoice` (scoped reads).

### Receipts / dunning / dispute alerts (reuse the Inc-8 engine)
- `NotificationService.dispatchPayment` → matrix + preferences/quiet-hours + the idempotent outbox +
  lease-claimed retry/backoff. New events `payment.receipt` / `payment.failed` / `payment.dispute`
  (+ matrix rows + templates). Receipts/dunning → owning customer; dispute alerts → org owner/finance
  (`resolveOrgStaffRecipients`). Dunning is urgent (bypasses quiet hours). The customer re-attempts pay
  from the app after a failure.

### Customer Pay surface (`apps/customer`)
- Real **`@stripe/stripe-react-native` PaymentSheet** behind a `StripeProvider` — the card never
  touches our app/API (only the client secret crosses; SAQ-A). A `Pay $X` CTA on the approved order →
  PaymentSheet → **polls `GET /orders/:id/payment` until the WEBHOOK confirms SUCCEEDED** (REST is the
  source of truth, like tracking — never "paid" on the client's say-so) → shows the receipt; retry on
  failure; "processing" if the webhook hasn't landed. Pure `payment-controller` (isPayable/payAmount/
  pollPaymentConfirmed) is unit-tested; `use-payment-sheet` wraps the real SDK.

## QC gate — findings + fixes (fix-verified)
- **(HIGH) Invoice race** — `generateInvoice` checked for an existing invoice OUTSIDE the tx, so a
  concurrent call / the auto-receipt path could hit the unique `number` constraint → 500. **Fixed:** the
  create now catches `P2002` → re-reads + returns the existing invoice (idempotent).
- **(Defense-in-depth) Read scoping** — `getPaymentForOrder`/`getInvoiceForOrder` queried by `orderId`
  only (access already gated by `getOrderForRead`, and orderId is a UUID, so not exploitable). **Fixed:**
  both now scope by the gated order's `org_id`, matching the refund service's pattern.
- **(Documented) Post-commit notification gap** — receipt/dunning/dispute notifications fire AFTER the
  webhook tx commits (and the event is in `ProcessedStripeEvent`, so a Stripe redelivery is a no-op),
  so a process crash in that exact window would skip a notification. The financial record is durable +
  correct; the notification is best-effort + re-sendable. **This is the same accepted pattern as the
  Inc-8 geofence engine** — now noted in `webhook.service.ts` fireSideEffects + here. A future recovery
  scan (committed payments with no receipt row → re-enqueue) would close it.
- Lenses with no findings: no-stub/real-integrations, webhook security + idempotency, money correctness,
  tenancy/RBAC (all PASS).

## As-built ↔ prompt reconciliations (the code won)
- **Payment + Invoice + PaymentStatus/PaymentMethod/InvoiceStatus already existed** (modelled since
  Inc 1). The migration is additive AROUND them; no enum values were dropped (keeps it reversible —
  partial-refund is modelled via `Payment.refundedAmount`, not a new enum value). NEW enums
  `RefundStatus`/`DisputeStatus` are clean CREATE TYPE / reverse DROP TYPE.
- **Payment timing**: PRD A2.2 says approval "authorizes payment"; A5.1 says "auto-charge on approval
  or on delivery per setting." We took the **charge-on-approval** tight default (customer-initiated Pay
  after QUOTE_APPROVED) with the capture-later seam ready — flag for the founder if on-delivery capture
  is wanted.
- **Refund timing nuance**: an authenticated owner/finance refund is the source of truth for the
  refund CEILING (atomic reserve at API time); the `charge.refunded` webhook then confirms + reconciles
  to Stripe's authoritative total. (Customer payment SUCCESS, by contrast, is webhook-only.)
- **RBAC**: pay = OWNER/RESIDENTIAL_CUSTOMER/ACCOUNT_ADMIN/ACCOUNT_STAFF (own order, scoped);
  refund/invoice/dispute-read = OWNER/FINANCE. The owner-app SCREENS for refunds/disputes/invoices are
  the next increment; the API + state are built + e2e-locked now.
- **Webhook tenancy** is resolved from OUR stored rows (by `stripe_payment_intent_id`/`stripe_charge_id`/
  `stripe_invoice_id`), never from event metadata — a forged `metadata.orgId` can't redirect a payment
  (metadata is used only for the ledger row). An unmapped event is recorded + no-op.
