## What shipped (the increment)
The platform was **already B2B-priced** (`PricingService.resolveRate`: account_override → account list → org-default list → `Service.base_rate`). This increment adds the **owner/web management** to set up a corporate account + buildings + a per-pound/per-item rate card + a join code, and the **engine** that makes a resident at a corporate building (or a join-code member) **pay individually but be priced on the corporate rate card**. `resolveRate` is REUSED unchanged — this increment changes *which account* prices an order, not *how* a rate resolves.

Two ways a member is tied to a corporate account (both built + e2e-locked):
1. **Building match (condo path)** — the booking's service point falls inside a corporate building's boundary → corporate pricing. Works end-to-end this increment, no customer-app change.
2. **Join code (TTC path)** — `POST /v1/corporate/redeem` grants a pricing membership → corporate pricing. Endpoint + engine built + tested now; the customer-app entry screen is the **next increment**.

## Key decisions (build to these)
- **Effective pricing account = a nullable `Order.pricingAccountId`** (FK → Account, `ON DELETE SET NULL`). `Order.accountId` stays the **payer** (the member's own account → PER_ORDER, RBAC scope, order list — all unchanged). `resolveRate` is called with `order.pricingAccountId ?? order.accountId`. This **decouples WHO IS PRICED from WHO PAYS** — chosen over re-parenting the order under the corporate account, which would corrupt RBAC scope (the member wouldn't own their order), the order list, and batch billing. `pricingAccountId` is only ever set when it differs from the payer (guarded), else NULL ⇒ default/residential pricing.
- **Building-match boundary v1 = address point + radius.** A `Site` with `geo` (PostGIS `geography(Point,4326)`) **and** `matchRadiusM` (metres, bounded [10, 5000]) is a corporate building. Match = real PostGIS `ST_DWithin(geo, point, matchRadiusM)`; ties broken by nearest centre (`ST_Distance`, `LIMIT 1`) → deterministic. The simplest reliable rule; postal/explicit-address match is a documented later option.
- **Membership is a dedicated `CorporateMembership` model, NOT a UserRole.** Deliberately pricing-only: it never widens order read/write scope (a join-code member can never see another member's orders, nor book under the corporate account). Member-facing reads (`GET /v1/corporate/memberships`) are **userId-scoped** in the service (the Message/Notification pattern). This is the strict tenancy choice — a `UserRole(scope=ACCOUNT)` on the corp account would have let a member book under it and read other members' orders.
- **Precedence at booking:** building match → membership → none. Building match wins (the physical address is the most specific, member-independent signal). The booking user (`principal.userId`) drives membership (self-serve); geo drives building match (works for any booker).
- **The booking carries an optional `serviceGeo` (lat/lng)** on `bookOrderSchema` — backward-compatible (existing callers + the unchanged customer app are unaffected; no `serviceGeo` ⇒ membership-or-default).

## API (`apps/api/src/corporate/*` + `orders/*`)
- **`CorporateController` (`/v1/corporate`)** — management OWNER/FINANCE only: `POST/GET/GET:id/PATCH accounts`, `GET/POST accounts/:id/buildings` + `PATCH buildings/:siteId`, `GET accounts/:id/rate-card` (every service with account rate · default rate · base · **resolved effective rate + source**) + `PUT accounts/:id/rate-card/items/:serviceId`, `POST accounts/:id/join-code`. Member surface (any authenticated user, no `@Roles`): `POST /redeem` (idempotent; bad/expired → 400), `GET /memberships` (userId-scoped).
- **`PricingAccountService` (orders module)** — `resolveForBooking({orgId, userId, payerAccountId, serviceGeo})` → `{pricingAccountId, source}` or null. Real PostGIS building match + membership lookup. Wired into `OrdersService.book` (sets `pricingAccountId` + prices the estimate on the effective account) and consumed by `QuoteService.build` (`order.pricingAccountId ?? order.accountId`).
- Rate card writes the **account-bound `PriceList` / `PriceListItem`** (the §9.2 catalog) — real rows, lazily creating the account's PriceList.
