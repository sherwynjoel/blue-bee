## Decisions
- **Thin additive API field (the one backend change):** the order read already carried the scalar `pricingAccountId`, but not the account NAME the indicator needs. Added `pricingAccount: { select: { name: true } }` to `FULL_INCLUDE` in `orders.service.ts` → the order detail/booking response now carries `pricingAccount: { name } | null`. **Read-only, no pricing logic, no §5.1 change.** Tenancy: the order's OWNER reads their OWN order (scope already enforced); the pricing account is a same-org corporate account that prices their order — they should see its name (no leak). Customer `OrderDetail` type updated (`pricingAccountId`, `pricingAccount`).
- **Two display sources, both server truth:**
  - **Pre-booking (BookScreen) + Settings:** `GET /v1/corporate/memberships` (userId-scoped) → the user's active membership name. A membership guarantees corporate pricing regardless of geo, so the badge is honest pre-booking.
  - **Post-booking (OrderDetailScreen):** `order.pricingAccount.name` → covers BOTH paths (a building match has no membership, but the order carries the resolved pricing account).
- **The client-side rough estimate (base-rate preview, honestly labeled) is UNCHANGED** — the app never recomputes corporate rates; the real quote is server-computed and reflects corporate pricing. The badge communicates "corporate pricing applies," not a client-derived number.
- **Degradation:** a failed memberships read just hides the badge (booking is never blocked or faked); a bad/expired code is a server 400 → a clean inline error. Redeem is idempotent (re-entry safe).
